# Database Overview

Akar is itself a database — a pure Rust embedded property graph database. This document describes its internal storage architecture, index structures, data formats, and durability model. Unlike traditional database documentation that describes how to use an external database, this document describes how Akar's own storage engine works internally.

---

## Storage Architecture

Akar's storage engine is a custom columnar disk-based engine designed for analytical workloads on graph data. It is not built on top of any existing database engine — every component (buffer manager, WAL, page manager, column storage, indexes) is implemented from scratch in pure Rust.

### Component Overview

| Component | Purpose | Key Design Choice |
|-----------|---------|-------------------|
| Buffer Manager | Page cache with eviction | Clock algorithm + mmap + NUMA awareness |
| Page Manager | Page allocation/deallocation | Buddy-system free space manager |
| Columnar Tables | Data storage | NodeGroup-based column-major layout |
| CSR Adjacency | Graph edge storage | Forward + reverse adjacency arrays |
| WAL | Durability | Typed records (Insert/Delete/Update) with CRC32 |
| Checkpoint | Persistence | Durable column mirrors + WAL truncation |
| ART Index | Primary key lookup | Adaptive Radix Tree (Node4/16/48/256) |
| HNSW Index | Vector similarity | Hierarchical Navigable Small World graph |
| Hash Index | Point lookup | In-memory + on-disk HashMap |
| Compression | I/O reduction | Constant, boolean, string dictionary encoding |

### Columnar Storage Model

Data is organized into **NodeGroups** — groups of rows stored column-major. Each NodeGroup contains one **ColumnChunk** per column. This layout is optimized for analytical workloads that scan entire columns rather than individual rows.

```
NodeGroup (NODE_GROUP_SIZE rows)
├── ColumnChunk[0] (column 0 data)
├── ColumnChunk[1] (column 1 data)
├── ColumnChunk[2] (column 2 data)
└── ...
```

Each ColumnChunk supports compression:
- **Constant encoding**: All values are the same; store once
- **Boolean encoding**: Bit-packed for boolean columns
- **String dictionary encoding**: Deduplicated string values via dictionary

### Graph Edge Storage (CSR)

Graph edges are stored in **Compressed Sparse Row (CSR)** format with both forward (outgoing) and reverse (incoming) adjacency arrays. Given a node ID, you can find all its neighbors in O(degree) time — this is the fundamental operation for graph traversal.

```
CSRAdjacency
├── Forward: node_id -> [edge_1, edge_2, ...]  (outgoing edges)
└── Reverse: node_id -> [edge_1, edge_2, ...]  (incoming edges)
```

## Index Types

### ART Index (Adaptive Radix Tree)

Primary key lookup and range scan. The ART is a radix tree that adapts its node type (Node4, Node16, Node48, Node256) based on the number of children, balancing memory usage and lookup speed. Keys are encoded via `ArtKey` (order-preserving encoding) to support efficient range scans.

| Node Type | Children | Memory | Use Case |
|-----------|----------|--------|----------|
| Node4 | 1-4 | 4 slots | Sparse keys |
| Node16 | 5-16 | 16 slots | Medium density |
| Node48 | 17-48 | 256 slots (indexed) | High density |
| Node256 | 49-256 | 256 direct slots | Very high density |

### HNSW Index (Vector Similarity)

Approximate nearest neighbor search for embedding vectors. HNSW builds a multi-layer graph where each node connects to its approximate nearest neighbors. Search starts at the top layer (sparse) and drills down to the bottom layer (dense), following the most promising neighbors at each level.

Supported distance metrics:
- Cosine similarity
- Euclidean (L2)
- Inner product

### Hash Index

Point lookup for exact-match queries. Two implementations:
- **In-memory**: `HashMap`-based, fast but not persisted
- **On-disk**: Persisted to disk, loaded into memory on database open

## Data Format

### Arrow-Native Execution

All data flows inside Akar as **Arrow-native DataChunks** — column-major batches of Arrow arrays. This is the interchange format between operators. The same format is used for:
- In-memory processing (operator pipeline)
- Parquet I/O (COPY FROM/TO)
- CSV I/O (COPY FROM/TO)
- TCP wire format (server mode)
- WASM output (get_next() returns row-major objects)

### File Layout

```
database_directory/
├── catalog.json          # System catalog (schemas, tables, types)
├── akar.lock             # Cross-process file lock
├── wal/                  # Write-Ahead Log
│   └── wal_*.log         # WAL segment files
├── fts/                  # Full-Text Search indexes
│   └── <idx>/            # Per-index Tantivy directory
├── tables/               # Columnar table data
│   └── <table_id>/       # Per-table directory
│       ├── columns/      # ColumnChunk files
│       └── indexes/      # ART/Hash/HNSW index files
└── overflow/             # Overflow pages for oversized values
    └── *.ovf             # Sidecar files
```

## Durability Model

Akar's durability model uses a **checkpoint-then-replay** strategy (P45.4, P60.2):

### Normal Operation
1. Writes go to in-memory NodeTable/RelTable (MVCC-hidden until publish)
2. Typed WAL records (Insert/Delete/Update) are appended to the WAL
3. WAL records are buffered per-transaction in LocalWAL
4. On commit: WAL records bulk-copied into global WAL after OCC validation

### Checkpoint
1. Persist all table data as durable column mirrors
2. Truncate the WAL
3. Mirrors are the authoritative source for recovery

### Crash Recovery
1. Load durable column mirrors (last checkpoint state)
2. Replay post-checkpoint WAL deltas on top
3. If data records were replayed: re-persist mirrors + checkpoint
4. Crash between akar commit and Tantivy FTS commit: index stale but uncorrupted (P107.3)

### Durability Guarantees
- **Committed transactions**: Always durable (WAL + checkpoint)
- **In-flight transactions**: Lost on crash (WAL not yet committed)
- **FTS index**: May be stale after crash (non-fatal; degrades searchability, never durability)
- **Recovery failure**: Database refuses to start (no silent empty-db fallback, P61.3)
