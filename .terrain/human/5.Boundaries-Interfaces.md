# System Boundaries & Interfaces

This document describes Akar's external interfaces — how a host program, a human at a terminal, or a foreign-language process actually *talks to* the engine. It covers the Rust API (canonical), the CLI, the C ABI, the Python bindings, the deprecated TCP broker, `SystemConfig`, the Cypher language contract, the extension trait, feature/environment flags, and the CI gates that bound the public contract. Parameter tables include a **meaning** column explaining design intent, not just type signatures.

---

## Rust API (canonical in-process interface)

**Description**: The primary way to use Akar — `Database::new` opens (or creates) a database directory, restores catalog + storage (WAL recovery), loads extensions, and hands out `Connection` handles whose `query`/`prepare` run the full parse → bind → plan → optimize → execute pipeline. Write statements wrap in explicit or implicit transactions ending at `commit_write_txn`.

**Key types**: `Database` (`akar-main/src/database.rs:149`), `Connection` (`akar-main/src/connection/query.rs:21`), `SystemConfig` (`akar-main/src/database.rs:34`), `QueryResult`.

**Minimal example**:
```rust
let db = Database::new("/path/to/db", SystemConfig::default())?;
let conn = db.connect()?;
let result = conn.query("MATCH (n:Person) RETURN n.name")?;
```

**Transaction control**: `begin_write_txn` / `commit_write_txn` (rollback alongside) via `akar-main/src/connection/transaction.rs:51-149` — commit performs OCC validation → WAL fsync → MVCC publish → FTS/HNSW index sync, strictly in that order (`3.Workflows.md` §2.2).

## Command-line interface (CLI)

**Description**: The `akar` binary (Cargo feature `cli`) provides a REPL and one-shot query execution for humans, scripts, and benchmarks. It is a thin shell over the Rust API — no separate execution path — so CLI behavior *is* production behavior.

**Entry**: `akar-cli/src/main.rs:34-44`. Output formatting via `OutputMode`.

| Parameter | Type | Required | Default | Meaning (design intent) |
|-----------|------|----------|---------|-------------------------|
| `<db_path>` | path | yes | — | Which database directory to open — identical directory semantics to the Rust API, so CLI and embedded usage share one storage contract |
| `--output <mode>` | `table\|json\|csv` | no | `table` | Marshalling only; `json`/`csv` exist so scripts can pipe results without a second tool, not to change query semantics |
| `--init-script <file>` | path | no | — | Run Cypher on startup (seed schema/data) — makes the REPL reproducible for demos and tests instead of hand-typing setup |
| `-c / --command <query>` | string | no | — | One-shot execution then exit — the non-interactive door CI and benchmarks use |

**Usage example**:
```bash
akar ./mydb --output json -c "MATCH (n:Person) RETURN n.name LIMIT 10"
```

## C ABI (`akar-c`)

**Description**: A flat, malloc-disciplined C surface for non-Rust embedders. Opaque handles + status codes; panics are caught and converted — no unwinding across FFI. `publish = false` (not on crates.io; link from source).

**Entry**: `akar-c/src/lib.rs` — lifecycle `akar_database_init` (`:95`) / `akar_database_destroy` (`:143`), `akar_connection_init` (`:168`) / `akar_connection_destroy` (`:196`), query `akar_connection_query` (`:229`), teardown `akar_error_message_free` (`:286`) / `akar_query_result_destroy` (`:306`).

| Symbol / param | Type | Meaning (design intent) |
|----------------|------|-------------------------|
| `akar_state` | enum (`:43`) | Success/failure code returned by every fallible call — callers branch on state *before* reading outputs, the C-idiomatic error discipline |
| `akar_system_config` | struct (`:9`) | POD mirror of `SystemConfig` — plain data both sides can agree on without shared Rust layout assumptions |
| `catch` wrapper (`:55`) | internal | Converts panics to `akar_state` + message — the panic firewall; without it a Rust bug would abort the host C program |
| `akar_error_message_free` (`:286`) | fn | Caller owns freeing error strings — explicit ownership because C has no RAII |
| `akar_query_result_destroy` (`:306`) | fn | Explicit result lifetime — results may hold large Arrow-backed buffers; deterministic release matters in C hosts |

**Usage sketch**:
```c
akar_system_config cfg = akar_default_system_config();
akar_database *db = akar_database_init("/path/to/db", cfg);
akar_connection *conn = akar_connection_init(db);
akar_query_result *res = akar_connection_query(conn, "MATCH (n) RETURN n LIMIT 5");
/* ... read rows ... */
akar_query_result_destroy(res);
akar_connection_destroy(conn);
akar_database_destroy(db);
```

## Python bindings (`akar-python`, PyO3)

**Description**: The ecosystem door for Python agent tooling and Sulur's tooling — `connect()` opens a database in-process (no server), query objects expose results, and `vector`/`fts` helpers surface extension capabilities. P123's direct in-process embedding path targets this surface. `publish = false`.

**Entry**: `akar-python` crate (workspace sibling of `akar-core/`).

```python
import akar
db = akar.connect("./memory_db")
rows = db.query("MATCH (n:Note) RETURN n.text ORDER BY n.created_at DESC LIMIT 10")
```

**Meaning**: Python gets the *same* engine, not a driver — embeddings, FTS, and GDS all run in the linked library, which is what makes the Sulur single-binary + Python-tooling story coherent (no sidecar process, per §13/ADR-004).

## TCP JSON broker (`akar-server`) — DEPRECATED for production (P124)

**Description**: Line-delimited JSON over TCP. **Demoted to test harness / wire reference**: Sulur is migrating to single-binary Rust embedding `akar-main` in-process. Do not target this interface for new production traffic.

**Meaning of the deprecation**: semantics were never *in* the broker — it mirrored `Connection`. Retiring it removes a network hop and a serialization tax without changing query behavior (the five-doors/one-`Connection` payoff, `4.Deep-Exploration/interfaces.md`).

## Configuration: `SystemConfig`

**Description**: The single configuration funnel — embedders configure in code, not config files (library-first posture; there is no TOML/YAML/env-file loader by design).

**Struct**: `akar-main/src/database.rs:34-69`.

| Field | Default (representative) | Meaning (design intent) |
|-------|--------------------------|-------------------------|
| `buffer_pool_size` | engine default | How much RAM the page cache may hold — the primary knob balancing speed vs. respect for the host process's memory (embedded DBs must share RAM politely) |
| `checkpoint_threshold` | 16 MiB | WAL size that triggers a checkpoint — bounds crash-recovery replay time; lower = faster recovery, more write amplification |
| `max_num_threads` | rayon default | Query parallelism ceiling — lets an embedder cap CPU use beside its own workloads instead of the engine grabbing every core |
| `spill_threshold` | engine default | When bulk ops spill to disk vs. stay in RAM — prevents a large `COPY FROM` from OOM-ing the host |
| `fts` / `vector` toggles | on (feature-gated) | Whether index capabilities register at open — feature flags decide compile-time inclusion; these decide runtime activation |
| salvage mode (`set_skip_wal`) | off | Open even with a corrupt WAL — an explicit, operator-chosen escape hatch; never automatic, because silently skipping the log hides data loss |

**Meaning**: every field is about *embedder sovereignty* — memory, CPU, and failure policy belong to the host, and the engine exposes them rather than hard-coding them.

## Query language contract (Cypher dialect)

**Description**: openCypher superset of the KuzuDB reference: **33 statement types** (reference 22), including akar-only vector/FTS/index/sequence/graph DDL, `Union`, `Merge`, `Analyze`, `LoadFrom` (SPEC §3.3). Binding is **case-sensitive** (wrong case → `Bind error: Table 'X' not found`) — matching the reference deliberately, so ported queries behave identically.

**FTS query syntax**: verbatim Tantivy `QueryParser` pass-through — terms, phrases, `+`/`-`/`AND`/`OR`, phrase-prefix, slop `~N`, field regex `/.../` (P106.2, SPEC §7). Meaning: no second query language to learn; the full-text power is the vendored engine's, documented upstream.

**Vector access**: standard `WHERE cosine_similarity(n.col, q) >= thr ORDER BY ... LIMIT k` — the optimizer recognizes the idiom (`VectorSimilarityDetection`, `akar-optimizer/src/passes/flat/vector_similarity.rs:54`) and rewrites it to an HNSW scan; explicit `CALL vector_similarity_scan(...)` also exists (P71.x). Meaning: portable query text with specialized execution — no proprietary syntax lock-in.

**EXPLAIN**: `EXPLAIN`, `EXPLAIN LOGICAL`, `EXPLAIN PROFILE` share the exact execution pipeline — what you introspect is what runs.

## Extension interface (`Extension` trait)

**Description**: The sole plugin contract — two methods, one lifecycle event (load once at `Database::new`, no hot reload).

| Method | Signature | Meaning (design intent) |
|--------|-----------|-------------------------|
| `name` | `fn name(&self) -> &'static str` | Stable identifier for diagnostics/ordering — `'static` avoids allocation and guarantees the name outlives the extension |
| `load` | `fn load(&self, context: &ExtensionContext) -> Result<(), String>` | One-shot registration into the engine — `Result` means a failed plugin aborts open cleanly instead of leaving half-registered functions |

**Source**: `akar-extension/src/lib.rs:20-28`; boot site `register_builtin_extensions` (`akar-main/src/database.rs:765`).

**Meaning**: the radical minimalism is the point — built-ins (`FtsExtension`, `VectorExtension`, `AlgoExtension`) use the *same* trait as third parties, so plugin authors exercise first-party code paths, and the contract has never needed a breaking change. To add a capability: new crate → impl `Extension` → add to registration (feature-gate heavy deps) → functions appear in `show_functions()`.

## Environment, feature flags & build gates

**Description**: Feature flags — not environment variables — are Akar's compile-time boundary mechanism (consistent with library-first: no hidden env magic). The CI gates are the runtime of the *contract*: what must hold before code merges.

| Flag / gate | Scope | Meaning (design intent) |
|-------------|-------|-------------------------|
| `cli` | `akar-cli` binary | Include the REPL — excluded for pure-library consumers who don't want a binary target |
| `fts-extension` / `vector-extension` | search capabilities | Compile BM25/HNSW in — off = smaller build for graph-only embedders |
| `duckdb-extension` / `sqlite-extension` | optional ETL | **Quarantines FFI** (`libduckdb-sys`, `rusqlite`) — default builds stay pure Rust (ADR-001); this is why two test gates exist |
| `wasm` | browser/edge build | Swap filesystem adapter — same pipeline, different substrate |
| Gate: `test [akar-core]` | default features, no `--all-features` | Official green/ red signal: **0 failed, 0 ignored** required; skips C++ DuckDB/SQLite compile + one networked httpfs test |
| Gate: `check [akar-core]` | release, `--all-features` | Pre-commit stricter pass — validates the full extension surface including C++ deps, faster than a full build |
| CI (`rust-ci.yml`) | every commit | `-Dwarnings` clippy + `cargo fmt --check` — the public contract includes "no warnings," so API slop fails the build, not code review |
| Fuzz targets | `akar-core/fuzz/fuzz_targets/` | `cypher_query`, `expression_eval`, `copy_from_csv`, `compression_roundtrip`, `wal_bytes` — nightly-only; encode "these five surfaces must never panic" as executable contract |

**Meaning**: the default-gate vs all-features split exists *because* of ADR-001 — pure-Rust purity and optional-FFI interoperability are both honored, with distinct gates keeping each honest.

## Integration recommendations

- **Embedding in a Rust host**: use the Rust API directly; size `SystemConfig` to your host's memory/CPU budget (`buffer_pool_size`, `max_num_threads`) rather than accepting defaults — the engine will share your process.
- **Python/Sulur tooling**: go through `akar-python`; treat P123's in-process embedding as the supported boundary (§13/ADR-004) — no TCP.
- **Non-Rust hosts**: the C ABI is the door; copy the `catch` + explicit-destroy discipline into your wrapper.
- **CI for downstream users**: mirror Akar's own split — a fast default-feature test gate plus an occasional `--all-features` check if you enable optional ETL extensions.
- **Do not**: build new production integrations on `akar-server`'s TCP broker (deprecated, P124); reach into `ExtensionContext` beyond its published surface; or assume env-var configuration exists — configuration is `SystemConfig` in code.
